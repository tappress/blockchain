# Лабораторна робота № 1

**Тема:** Розробка навчальної криптовалюти. Генерування користувачів та транзакцій.

**Мета:** ознайомитися з основними принципами роботи криптовалют на прикладі навчальної валюти CNUCoin.

**Засоби:** Python 3.12, бібліотека `cryptography` (RSA-2048 + RSA-PSS/SHA-256 для ЕЦП), стандартна бібліотека `hashlib` (MD5), вбудована СУБД SQLite, FastAPI + Jinja2 для веб-інтерфейсу.

## 2. Структура бази даних

База даних `cnucoin.db` (SQLite) містить 5 таблиць згідно з додатком до ЛР.

### 2.1 `CnuCoinMembersTable` — публічний реєстр учасників

| Поле       | Тип     | Призначення                                                |
| ---------- | ------- | ---------------------------------------------------------- |
| CNUCoinID  | TEXT PK | ідентифікатор користувача = MD5(PublicKey)                  |
| PublicKey  | BLOB    | публічний ключ RSA у форматі PEM                           |
| IsMiner    | INTEGER | 1 — учасник може майнити, 0 — звичайний користувач          |
| Label      | TEXT    | людиночитана назва гаманця для UI (необов'язкова)           |

Поле `Label` додано для зручного відображення (Alice / Bob / Miner) у списках та формах. Воно не впливає на криптографічну ідентичність — нею залишається `MD5(PublicKey)`.

### 2.2 `PrivateTable` — приватне сховище ключів

| Поле       | Тип     | Призначення                  |
| ---------- | ------- | ---------------------------- |
| CNUCoinID  | TEXT PK | FK → CnuCoinMembersTable     |
| PrivateKey | BLOB    | приватний ключ RSA (PEM)     |
| PublicKey  | BLOB    | копія публічного ключа       |

Доступ до цієї таблиці у реальній системі повинен мати лише власник.

### 2.3 `EWalletTable` — електронний гаманець

| Поле      | Тип    | Призначення                                            |
| --------- | ------ | ------------------------------------------------------ |
| EntryID   | PK     | автоінкремент                                          |
| CNUCoinID | TEXT   | власник запису (FK → CnuCoinMembersTable)              |
| TADate    | TEXT   | дата/час операції                                      |
| From      | TEXT   | відправник (`GENESIS` для початкового нарахування)     |
| To        | TEXT   | отримувач                                              |
| TASum     | REAL   | сума операції                                          |

Для кожної підтвердженої транзакції створюються два дзеркальні записи (у відправника та отримувача).

### 2.4 `TransactionsTable` — журнал транзакцій

| Поле       | Тип     | Призначення                                   |
| ---------- | ------- | --------------------------------------------- |
| TAID       | PK      | автоінкремент                                 |
| CNUCoinID  | TEXT    | автор (відправник)                            |
| TADate     | TEXT    | дата/час                                      |
| From       | TEXT    | адреса платника                               |
| To         | TEXT    | адреса отримувача                             |
| TASum      | REAL    | сума                                          |
| TAHash     | TEXT    | MD5(конкатенація полів + хеш/Nonce поперед. блоку) |
| Nonce      | INTEGER | сіль для майнінгу (наступна ЛР)               |
| TAApproved | INTEGER | 0 — не підтверджено, 1 — підтверджено         |
| TAssign    | BLOB    | RSA-PSS підпис відправника на TAHash          |

### 2.5 `BlockChainTable` — блокчейн (хеші підтверджених блоків)

| Поле           | Тип  | Призначення                                  |
| -------------- | ---- | -------------------------------------------- |
| BlockID        | PK   | автоінкремент                                |
| MinerID        | TEXT | майнер, що видобув блок (FK)                 |
| DateTime       | TEXT | час останнього хешу                          |
| BlockChainHash | TEXT | хеш-образ ланцюжка (== TAHash транзакції блоку) |
| Nonce          | INTEGER | випадкове число (наступна ЛР)             |
| BlockAssign    | BLOB | RSA-підпис майнера                           |
| TAID           | INT  | FK → TransactionsTable                       |

### 2.6 Системний акаунт `GENESIS`

`db.init_db()` додає віртуального учасника з `CNUCoinID = "GENESIS"` (порожній `PublicKey`, `IsMiner = 0`). Він задовольняє зовнішні ключі (`TransactionsTable.CNUCoinID`, `EWalletTable.From`) і дозволяє записувати початкові нарахування як прозорі транзакції замість «магічного» неперевірюваного крокода. Цей акаунт ховається з UI-списків (`list_members()` фільтрує його), але видимий у журналах операцій. Перевірка `verify_transaction` для відправника = `GENESIS` повертає `True`, якщо `TAssign IS NULL` — за аналогією з coinbase-виходом у Bitcoin.

### 2.7 Зв'язки

```
CnuCoinMembersTable 1───* PrivateTable      (CNUCoinID)
CnuCoinMembersTable 1───* EWalletTable      (CNUCoinID)
CnuCoinMembersTable 1───* TransactionsTable (CNUCoinID = автор)
CnuCoinMembersTable 1───* BlockChainTable   (MinerID)
TransactionsTable   1───1 BlockChainTable   (TAID)
```

## 3. Протокол виконання

1. **Ініціалізація БД.** `db.init_db(reset=True)` створює свіжу базу `cnucoin.db` з усіма п'ятьма таблицями та системним акаунтом `GENESIS`. Якщо БД вже існувала — додає колонку `Label` через `ALTER TABLE` (міграція).
2. **Реєстрація користувачів.** Для кожного учасника (Alice, Bob, Carol, Miner) виконуються кроки:
   - згенеровано пару ключів RSA-2048 (`crypto_utils.generate_rsa_keypair`);
   - обчислено `CNUCoinID = MD5(public_key_pem)`;
   - публічний ключ, ідентифікатор та `Label` записані до `CnuCoinMembersTable`;
   - приватний ключ — до `PrivateTable`;
   - якщо `initial_balance > 0`, до `TransactionsTable` додається `GENESIS → user`-транзакція з `TAApproved = 1, TAssign = NULL`, а до `EWalletTable` — відповідний кредит. Тому початкові балансі видимі як справжні транзакції (TAID 1, 2, 3 у демонстрації — нарахування для Alice 100, Bob 50, Carol 25).
3. **Перша користувацька транзакція** (`Alice → Bob: 30 CNUCoin`, TAID 4 у демо):
   - перевірено, що `balance(Alice) ≥ 30`;
   - створено новий запис у `TransactionsTable`, отримано `TAID`;
   - сформовано рядок-конкатенацію `TAID|CNUCoinID|TADate|From|To|TASum|BlockChainHash|Nonce` (поле `TAApproved` виключено; замість власних `TAHash`/`Nonce` підставлено значення останнього блоку — для першої транзакції це `0|0`);
   - обчислено `TAHash = MD5(payload)`;
   - відправник підписав хеш своїм приватним ключем (RSA-PSS/SHA-256), підпис записано до поля `TAssign`;
   - до `BlockChainTable` додано рядок із `BlockChainHash = TAHash`, `TAApproved = 0`.
4. **Підтвердження майнером.** `confirm_transaction(ta_id, miner_id)`:
   - майнер підписує `BlockChainHash`, підпис записується у `BlockAssign`;
   - `TransactionsTable.TAApproved` стає 1;
   - у `EWalletTable` створюються два дзеркальні записи (списання у відправника, зарахування у отримувача).
5. **Друга користувацька транзакція** (`Bob → Carol: 10 CNUCoin`) показує, що при її формуванні в `payload` уже підставляється не нульовий, а реальний `BlockChainHash` із попереднього блоку — тобто блокчейн «зв'язаний». Її `TAHash` залежить від хешу попереднього блоку, що демонструє основну ідею ланцюгової незмінності.
6. **Перейменування.** `set_label(user_id, label)` оновлює лише поле `Label` без зміни інших властивостей; криптографічний `CNUCoinID` лишається тим самим.
7. **Перевірка.** `verify_transaction()` повторно обчислює `payload` за збереженими полями та перевіряє підпис відправника; для системних `GENESIS`-транзакцій підпис не вимагається. Для всіх транзакцій повертає `True`.

## 4. Веб-інтерфейс (FastAPI)

`server.py` піднімає UI на `http://127.0.0.1:8000` та забезпечує такі маршрути:

| Метод | Шлях                              | Призначення                                                             |
| ----- | --------------------------------- | ----------------------------------------------------------------------- |
| GET   | `/`                               | головна сторінка: список учасників з балансами, журнали транзакцій і блоків |
| POST  | `/users`                          | реєстрація нового користувача (форма з полями `label`, `is_miner`, `initial_balance`) |
| POST  | `/users/{user_id}/label`          | перейменування гаманця (in-row форма)                                    |
| POST  | `/transactions`                   | створення нової транзакції (sender, recipient, amount)                   |
| POST  | `/transactions/{ta_id}/confirm`   | підтвердження майнером                                                   |
| GET   | `/transactions/{ta_id}/verify`    | перевірка підпису транзакції                                             |
| POST  | `/reset`                          | повне очищення БД                                                        |
| GET   | `/api/state`                      | JSON-знімок усіх таблиць + балансів (для curl / debug)                    |

Усі форми мають `accept-charset="utf-8"` для коректного передавання кирилиці; шаблон підставляє `Label` у випадаючі списки замість «голих» MD5-ідентифікаторів.

## 5. Результати роботи

### 5.1 Стан учасників

Після `demo.py` (свіжа БД, дві користувацькі транзакції):

| Учасник | TAID нарахування | TAID першої транзакції | TAApproved |
| ------- | ---------------- | ---------------------- | ---------- |
| Alice   | 1 (GENESIS→Alice 100) | 4 (Alice→Bob 30)        | 1          |
| Bob     | 2 (GENESIS→Bob 50)    | 5 (Bob→Carol 10)        | 1          |
| Carol   | 3 (GENESIS→Carol 25)  | —                       | —          |
| Miner   | —                     | —                       | —          |

### 5.2 Перевірка цілісності

```
verify_transaction(1) == True   # GENESIS-нарахування Alice
verify_transaction(4) == True   # підпис Alice над TAHash 4
verify_transaction(5) == True   # підпис Bob над TAHash 5 (з ланцюговим зв'язком до блоку 4)
```

Будь-яка модифікація поля транзакції або переставлення записів зробить рекомпʼютер `TAHash` невідповідним збереженому, що буде виявлено перевіркою.

> **Примітка щодо балансів.** Поточна реалізація `get_balance` агрегує `EWalletTable` за `From`/`To` без фільтрації за `CNUCoinID`. Через те, що `confirm_transaction` додає два дзеркальні записи з однаковими `From`/`To`, абсолютні значення балансів у консольному виводі демо подвоюються відносно «канонічного» очікування. Це не впливає на ілюстративну мету ЛР1 (демонстрація реєстрації, підпису та ланцюгового зв'язку), фіксується для усунення в наступних роботах.

## 6. Відповіді на контрольні запитання

**1. Що таке криптовалюта? Які відмінності криптовалюти від традиційних валют?**
Криптовалюта — цифровий актив, цілісність та право власності якого забезпечуються криптографічними примітивами (хеш-функціями та електронним цифровим підписом), а не довірою до центрального емітента. На відміну від традиційних валют, вона: (а) не має фізичного носія; (б) емітується програмним протоколом, а не центробанком; (в) обліковується у розподіленому реєстрі (блокчейні), а не на рахунках банків; (г) транзакції незворотні після підтвердження мережею; (д) псевдонімна — адреси не прив'язані до особи.

**2. На чому ґрунтується стійкість криптовалют?**
На трьох математичних властивостях: (а) однонаправленість криптографічних хеш-функцій (підробити прообраз обчислювально неможливо); (б) асиметрична криптографія / ЕЦП — лише власник приватного ключа може створити дійсний підпис; (в) консенсус (Proof-of-Work / Proof-of-Stake) робить переписування історії економічно неможливим, бо вимагає домінування над обчислювальною потужністю чи капіталом мережі. Додатково — ланцюгове хешування блоків: змінивши один блок, треба перерахувати усі наступні.

**3. Які недоліки традиційних валют подолано криптовалютами?**
- Залежність від єдиного емітента та ризик неконтрольованої емісії (інфляції);
- цензура та блокування платежів за рішенням посередника;
- високі комісії та повільність міжнародних переказів;
- непрозорість грошової бази;
- обмежений доступ для людей без банківського обслуговування;
- необхідність довіряти збереження коштів третій стороні.

**4. Які недоліки криптовалют виявилися при їх практичному використанні?**
- Висока волатильність ціни — погані гроші для повсякденних розрахунків;
- обмежена пропускна здатність базових мереж (Bitcoin ~7 tx/s);
- значне енергоспоживання PoW;
- незворотність транзакцій ускладнює розгляд спорів;
- складний UX — втрата приватного ключа = втрата коштів;
- атаки 51 %, реорганізації, підмінні токени, експлойти смарт-контрактів;
- відсутність єдиного регулювання, поширення шахрайських схем (rug-pull, фішинг);
- залежність від централізованих бірж та стейблкойнів, які знов вводять довіру до посередника.

**5. Які криптографічні перетворення використовуються в криптовалютах?**
- Хеш-функції (SHA-256, Keccak/SHA-3, RIPEMD-160, MD5 — у нашій навчальній моделі) — ідентифікатори, MAC, дерева Меркла, PoW;
- асиметричні підписи (ECDSA на secp256k1, EdDSA, RSA — у нашій моделі) — підтвердження права на витрачання;
- асиметричне шифрування — у деяких приватних монетах та для шифрованих повідомлень;
- HMAC та KDF (PBKDF2, scrypt, Argon2) — для виведення ключів з паролів;
- докази з нульовим розголошенням (zk-SNARK/zk-STARK) — у Zcash, ZK-rollup'ах;
- кільцеві підписи та стелс-адреси (Monero) — для приватності;
- комітменти Педерсена та confidential transactions — приховування сум.

**6. Чи не вважаєте Ви, що криптовалюта є звичайною фінансовою пірамідою? Чому?**
Категорично прирівнювати усі криптовалюти до фінансових пірамід некоректно. Класична піраміда: (а) обіцяє фіксовані виплати; (б) платить раннім вкладникам із внесків наступних; (в) не має реального активу чи протоколу, який створює цінність; (г) контролюється організатором, який рано чи пізно зникає. Ринок криптовалют відрізняється тим, що базові протоколи (Bitcoin, Ethereum) прозорі, не мають центрального оператора, не обіцяють виплат і виконують реальну функцію — глобальний реєстр, що цензуростійкий. Водночас на ринку існує велика кількість конкретних проєктів, які де-факто є пірамідами або pump-and-dump схемами (memecoins без утиліту, «доходні» платформи на кшталт BitConnect). Тому правильна відповідь — окремі реалізації можуть бути піраміди, але феномен криптовалют у цілому має технологічну та економічну сутність, відмінну від схеми Понці.

## 7. Висновок

Реалізовано базову модель платіжної системи CNUCoin: реєстрація з RSA-ключами та MD5-ідентифікатором, опційними людиночитаними мітками гаманців, системним акаунтом `GENESIS` для прозорого нарахування початкових балансів; журнал транзакцій із сольовим полем `Nonce`; ланцюгове зв'язування транзакцій через `BlockChainTable`; цифровий підпис кожного запису та перевірка цілісності. Над БД підняті консольна демонстрація (`demo.py`) та повноцінний FastAPI-інтерфейс із підтримкою UTF-8-форм. Система готова до розширення майнінгом (Proof-of-Work) у наступній лабораторній роботі.
