## 1. Функціональні вимоги

| № | Вимога |
|---|---|
| F1 | Реєстрація учасників системи з трьома ролями: `student`, `teacher`, `registrar`. Для кожного учасника генерується пара ключів RSA-2048 і обчислюється унікальний ідентифікатор `MemberID = MD5(PublicKey)` |
| F2 | Зберігання приватного ключа окремо від публічного (відповідно дві таблиці: `MembersTable` — публічна, `PrivateTable` — приватна) |
| F3 | Управління навчальними дисциплінами (назва, кредити, семестр) |
| F4 | Виставлення оцінки викладачем: запис типу (викладач, студент, дисципліна, бал 0..100, коментар) підписується приватним ключем викладача (RSA-PSS + SHA-256) |
| F5 | Підтвердження оцінки реєстратором через Proof-of-Work: пошук Nonce такого, що `MD5(GradeHash ‖ prev_BlockHash ‖ Nonce)` починається з `difficulty` нульових символів |
| F6 | Верифікація оцінки: перевірка цілісності даних (рекомпʼютер `GradeHash`) та підпису викладача |
| F7 | Верифікація блоку: рекомпʼютер `BlockHash`, перевірка PoW-цілі, перевірка підпису реєстратора |
| F8 | Верифікація всього ланцюга (`/chain/verify`): обхід усіх блоків і всіх схвалених оцінок |
| F9 | Перегляд транскрипту студента: список оцінок із коментарями, обчислення зваженого середнього (GPA) та конвертація у ECTS-літеру (A, B, C, D, E, FX, F) |
| F10 | Веб-інтерфейс (FastAPI + Jinja2) для всіх дій + JSON API для скриптового доступу |

## 2. Нефункціональні вимоги

| № | Вимога |
|---|---|
| N1 | **Незмінність:** після підтвердження оцінки її поля не можна змінити непомітно — зміна `Mark` чи `Comment` поламає `GradeHash`, який підписаний викладачем |
| N2 | **Тампер-евіденція:** ретроактивна зміна історії потребує перерахунку всіх PoW-блоків, що йдуть після зміненого. Складність зростає експоненційно з difficulty |
| N3 | **Розмежування ролей:** лише `teacher` може підписати оцінку, лише `registrar` — підтвердити її через PoW; ролі перевіряються на рівні бізнес-логіки |
| N4 | **Локалізація:** інтерфейс і повідомлення українською; UTF-8 без втрат у формах (`accept-charset="utf-8"`) |
| N5 | **Простота розгортання:** одна команда `make project` піднімає сервер, одна `make demo-project` запускає end-to-end демонстрацію |
| N6 | **Освітня прозорість:** усі первинні дані доступні через `/api/state`, доступний JSON-знімок усіх таблиць для аудиту |

## 4. Структура блокчейну

База даних SQLite, п'ять таблиць (відповідає вимозі лабораторної №1, розширена ролями та дисциплінами):

### `MembersTable` — публічний реєстр
```sql
MemberID    TEXT PRIMARY KEY     -- MD5(PublicKey)
PublicKey   BLOB NOT NULL
Role        TEXT NOT NULL        -- student | teacher | registrar
Label       TEXT NOT NULL        -- ПІБ
GroupCode   TEXT                 -- академгрупа (тільки для студентів)
```

### `PrivateTable` — приватні ключі (FK до `MembersTable`)
```sql
MemberID    TEXT PRIMARY KEY
PrivateKey  BLOB NOT NULL
PublicKey   BLOB NOT NULL
```

### `CoursesTable` — дисципліни
```sql
CourseID    INTEGER PRIMARY KEY AUTOINCREMENT
Name        TEXT NOT NULL
Credits     REAL NOT NULL
Semester    INTEGER NOT NULL
```

### `GradesTable` — журнал оцінок (аналог транзакцій)
```sql
GradeID     INTEGER PRIMARY KEY AUTOINCREMENT
TeacherID   TEXT NOT NULL        -- автор підпису
StudentID   TEXT NOT NULL        -- субʼєкт оцінки
CourseID    INTEGER NOT NULL
GradeDate   TEXT NOT NULL
Mark        INTEGER NOT NULL     -- 0..100
Comment     TEXT
GradeHash   TEXT                 -- MD5 над полями оцінки
Nonce       INTEGER              -- знайдений при підтвердженні
Approved    INTEGER NOT NULL DEFAULT 0
TeacherSign BLOB                 -- RSA-підпис викладача над GradeHash
```

### `BlockChainTable` — ланцюг блоків
```sql
BlockID         INTEGER PRIMARY KEY AUTOINCREMENT
RegistrarID     TEXT
DateTime        TEXT NOT NULL
BlockHash       TEXT NOT NULL    -- MD5(GradeHash | prev_BlockHash | Nonce)
Nonce           INTEGER NOT NULL
RegistrarSign   BLOB             -- RSA-підпис реєстратора над BlockHash
GradeID         INTEGER          -- оцінка, яку підтверджує блок
```

**Розподіл відповідальностей:**

| Рівень | Що захищає | Чим захищає |
|---|---|---|
| Поле `GradeHash` | Цілісність полів оцінки | MD5-дайджест над `(GradeID, TeacherID, StudentID, CourseID, Date, Mark, Comment)` |
| Поле `TeacherSign` | Авторство оцінки | RSA-PSS-підпис викладача над `GradeHash` |
| Поле `BlockHash` | Звʼязок блоку з ланцюгом + PoW-витрати | MD5(`GradeHash` ‖ `prev_BlockHash` ‖ `Nonce`), починається з `0…` |
| Поле `RegistrarSign` | Авторство підтвердження | RSA-PSS-підпис реєстратора над `BlockHash` |

## 5. Алгоритми

### 5.1. Генерація ідентичності
```
private_key, public_key ← RSA-2048 (PUBLIC_EXPONENT=65537)
MemberID = MD5(public_key_PEM)
```
RSA-2048 із серіалізацією у PEM (PKCS#8 для приватного ключа, SubjectPublicKeyInfo для публічного). Вибір MD5 для ID — згідно зі специфікацією лабораторних робіт; для виробничої системи слід використати SHA-256.

### 5.2. Хешування оцінки
```
GradeHash = MD5(
    str(GradeID) | TeacherID | StudentID | str(CourseID) |
    GradeDate    | str(Mark)  | Comment
)
```
Без ланцюгових полів — це свідоме архітектурне рішення (див. розділ 6 «Обмеження та компроміси»). Звʼязок із ланцюгом покладено повністю на рівень блоку.

### 5.3. Цифровий підпис (ЕЦП)
- Алгоритм: **RSA-PSS** з функцією маскування MGF1 над SHA-256, параметр `salt_length = MAX_LENGTH`.
- Підписувач (викладач) обчислює `signature = sign(GradeHash, private_key)`.
- Перевірка: `verify(signature, GradeHash, public_key)` повертає True, якщо обидві сторони використали ключову пару, що відповідає `MemberID = MD5(public_key)`.

### 5.4. Proof-of-Work
```
target = "0" * difficulty
nonce  = 0
repeat:
    payload = f"{GradeHash}|{prev_BlockHash}|{nonce}"
    digest  = MD5(payload)
    if digest startswith target: break
    nonce += 1
BlockHash = digest
```
Складність 1 (1 нульовий шістнадцятковий символ) обрано для демонстраційних цілей: математичне очікування — **16 спроб** на блок. Для difficulty=N очікування — `16^N` спроб. Це дозволяє наочно показати квадратичне зростання витрат при підвищенні складності.

### 5.5. Верифікація: три рівні
1. **Підпис оцінки** (`verify_grade`): рекомпʼютер `GradeHash` із поточних полів → порівняння з `TeacherSign` через RSA-PSS-перевірку.
2. **Блок** (`verify_block`): рекомпʼютер `BlockHash` з поточних `GradeHash`, `prev_BlockHash` та збереженого `Nonce` → перевірка нульового префіксу → перевірка `RegistrarSign`.
3. **Цілий ланцюг** (`verify_chain`): обхід усіх блоків + усіх схвалених оцінок; повертає список усіх знайдених порушень.

## 6. Обмеження та компроміси

| Компроміс | Обґрунтування |
|---|---|
| **Підтвердження «на місці» (без deferred-confirmation з Лабораторної №2)** | У академічному контексті реєстратор — це довірена сторона (деканат), не конкуруючий майнер. PoW тут служить виключно для тампер-евіденції, тож ігровий стимул «наступний майнер платить попередньому» не потрібен. Підтвердження одразу після видобутку блоку спрощує UX без втрати безпеки |
| **MD5 замість SHA-256** | Дотримання специфікації лабораторних робіт. Усі хеш-функції викликаються через одну обгортку `crypto_utils.md5_hex`, тож при потребі їх можна замінити одним рядком |
| **Без P2P-консенсусу** | Один SQLite-файл моделює «мережу». Це достатньо для демонстрації принципів цілісності, але не масштабованості/децентралізації |
| **Без динамічної складності** | Difficulty фіксована (1). У продакшні Bitcoin кожні 2016 блоків перераховує цільове значення; тут це знято для простоти |
| **Викладач підписує тільки поля оцінки, без ланцюгового звʼязку** | Альтернатива (як у Лаб. №2 — підписувати з включеним `prev_BlockHash`) ускладнює верифікацію, коли оцінки створюються пакетно й майнінг відстає. Розділення «викладач атестує зміст; ланцюг атестує порядок» — чистіше архітектурно |

## 7. Структура коду проєкту

```
project/
├── crypto_utils.py     # RSA-2048, MD5, RSA-PSS sign/verify
├── db.py               # SQLite-схема + ініціалізація
├── gradebook.py        # бізнес-логіка (register, post_grade, mine_next, verify_*)
├── server.py           # FastAPI маршрути + Jinja2-шаблон
├── demo.py             # демонстрація end-to-end у консолі
├── templates/
│   └── index.html      # головна сторінка
├── REPORT.md           # цей звіт
└── gradebook.db        # SQLite-файл (створюється на ходу)
```

### Основні модулі
- `gradebook.register_member(role, label, group_code)` — створює керівника, викладача чи студента
- `gradebook.post_grade(teacher, student, course, mark, comment)` — викладач підписує запис
- `gradebook.mine_next(registrar, difficulty)` — реєстратор шукає Nonce (PoW)
- `gradebook.verify_grade(grade_id) → bool` — перевіряє цілісність та підпис
- `gradebook.verify_block(block_id) → bool` — перевіряє блок
- `gradebook.verify_chain() → dict` — повний аудит
- `gradebook.transcript(student_id) → list[dict]` — журнал студента
- `gradebook.gpa(student_id) → float | None` — зважений середній бал
- `gradebook.ects_letter(mark) → str` — конвертація бала в ECTS-літеру

### Маршрути FastAPI
- `GET /` — головна; `?student_id=…` показує транскрипт
- `POST /members`, `POST /members/{id}/label` — реєстрація / перейменування
- `POST /courses` — додання дисципліни
- `POST /grades` — виставлення оцінки
- `POST /mine` — підтвердження PoW
- `GET /grades/{id}/verify`, `GET /blocks/{id}/verify`, `GET /chain/verify` — аудит
- `POST /reset` — очищення БД (для повторного запуску демонстрації)
- `GET /api/state`, `GET /api/transcript/{id}`, `GET /api/chain/verify` — JSON API

## 9. Відповіді на контрольні запитання

### 9.1. Опис проєкту, архітектури, технологій та алгоритмів

Проєкт — це електронна залікова книжка, у якій кожна оцінка фіксується як підписаний викладачем запис у блокчейні, що зберігається у локальній SQLite-базі. Архітектура трирівнева: HTML/Jinja2 → FastAPI → бібліотечний шар (модулі `gradebook`, `crypto_utils`, `db`). Технології: Python 3.12, FastAPI, Jinja2, SQLite, бібліотека `cryptography` для RSA, стандартна `hashlib` для MD5, менеджер пакетів — `uv`. Алгоритми: RSA-2048 для ключів і RSA-PSS+SHA-256 для підписів; MD5 для ідентифікаторів та хешів блоків; Proof-of-Work з пошуком Nonce, який дає `MD5(...)` із заданою кількістю провідних нулів; верифікація на трьох рівнях (запис → блок → ланцюг).

### 9.2. Означення блокчейну. Для чого він тут?

Блокчейн — це структура даних, у якій записи групуються в блоки, кожен наступний блок криптографічно посилається на попередній (через хеш), а додавання блоку коштує обчислювальної роботи (PoW). Це забезпечує **незмінність історії**: щоб ретроактивно змінити запис, треба перерахувати весь PoW від цієї точки до останнього блоку.

У цьому проєкті блокчейн дає три ключові переваги порівняно з простою SQL-табличкою з підписами:

1. **Тампер-евіденція на рівні бази:** якщо адміністратор бази даних спробує тихо змінити Mark з 58 на 95, перевірка оцінки одразу провалиться (рекомпʼютеру `GradeHash` ≠ збережений). У звичайній БД така зміна не залишить слідів.
2. **Криптографічно прив'язана авторизація:** кожна оцінка має RSA-підпис викладача над хешем; підробити підпис без приватного ключа неможливо.
3. **Аудит однією командою:** `verify_chain()` дає бінарну відповідь «база в порядку / база скомпрометована», з переліком усіх порушень. У SQL-системі перевірка цілісності — окремий складний процес.

### 9.3. Перспективи блокчейну в інформаційному світі

Найперспективніші напрями: (1) **системи документообігу та посвідчень** — дипломи, ліцензії, нотаріальні документи, де підробка має високі наслідки; (2) **ланцюги постачання** — відстеження походження товарів від виробника до полиці; (3) **DeFi і токенізовані активи** — мікроплатежі, NFT для прав на контент; (4) **самосуверенна ідентичність (SSI)** — користувач сам тримає ключі та контролює, кому розкривати які атрибути. Поточні обмеження — енергоємність PoW (рішення: PoS, ZK-rollups), низька пропускна здатність (рішення: L2-рішення, шардинг) та регуляторна невизначеність. У освіті блокчейн дає верифіковані академічні досягнення — приклад, реалізований у цьому проєкті.

## 10. Висновки

У ході виконання проєкту була розроблена повноцінна електронна залікова книжка на основі блокчейн-технологій. Система демонструє три ключові гарантії, які забезпечує блокчейн: **криптографічну авторизацію** (RSA-підпис викладача), **незмінність історії** (PoW + ланцюговий звʼязок) та **публічну верифікованість** (будь-яка стороння особа з доступом до бази може запустити повний аудит). Проєкт побудовано на основі методів, набутих у Лабораторних роботах №1–2: ідентичність через MD5(PublicKey), підпис записів, Proof-of-Work з ціллю-нульовим префіксом. Кінцева система комплектується консольним демо (`make demo-project`), що проходить наскрізний сценарій (реєстрація → виставлення оцінок → майнінг → транскрипт → перевірка ланцюга → детекція спроби підробки) і веб-інтерфейсом (`make project`), що дозволяє інтерактивно виконувати всі ті ж дії.
